# ADR-005: Manual review page for model decisions

**Date:** 2026-11-13
**Status:** Accepted
**Relates to:** [PRD §14](../PRD.md#14-amendment-2026-11-13-manual-review-of-model-decisions), [ADR-003](003-photo-reading-decisions.md), [ADR-004](004-report-and-cli.md)

---

## 1. Context

The reference labels for street photos and sign crops were produced by AI agents (PRD AC-29). The accuracy in the report is therefore agreement between models, not correctness. The human wants to judge the model decisions directly, in a session short enough to finish (at most 100 items, by default the 55 image–question pairs of the sample), and to hand the judgments back to the agent as a file.

The human decided on 2026-11-13:

- a single static HTML + JavaScript file is enough; no Streamlit, Gradio, Label Studio, Langfuse or Promptfoo;
- blind review first, then reveal (PRD AC-34);
- results stay on the page and in the downloaded JSON; the reports are not changed;
- image quality is recorded as a review flag only; sign crops are not re-cut in this change.

## 2. Decisions

### D-51 Static page generated by `map-qa review export`

**Decision.** A new subcommand `map-qa review export [--config] [--output-dir] [--max-items N]` rebuilds the sample with the same `SamplePlanner` and `ImagePreparer` as the run, reads every answer through `Escalator` with the run's cache, and writes `<output_dir>/review/review.html` plus `review/images/<image_sha256>.jpg` and `review/context/<photo_id>.jpg`. No model request is possible: the escalator gets a ledger in a temporary directory with `max_requests = 0` and a client that fails if called, so a missing cache entry becomes a "not reviewable" item and nothing is written to the real `ledger.jsonl`.

**Why the cache and not `results.json`.** `results.json` keeps only the top probability and no image hash. The cache holds the full response bodies (all probabilities, tier-2 certainty, the questions of each tier-2 request), so the page can show exactly what each model returned.

**Rejected alternatives.**
- Streamlit / Gradio: a server and new dependencies for at most 100 items.
- Label Studio: best for large annotation work, but needs a server and a database.
- Langfuse: annotation queues on traces, but needs self-hosting or sending photos and prompts to a cloud service, and manual instrumentation of the Decisions API.
- Promptfoo: compares prompt versions by re-running them, which conflicts with the cache, the budget and D-33 (no retries). It may help later to compare `qs-v1` with a future `qs-v2`.

### D-52 JavaScript exception for the review page only

**Decision.** ADR-004 §3.4 ("static, no JS") stays in force for `report.html` and `summary.html`. `review/review.html` is the only output with JavaScript, because a form that keeps state and produces a file cannot work without it. Constraints:
- one file, inline CSS and JS, no external scripts, fonts or styles, no `fetch`, no network requests;
- item data is embedded as `<script type="application/json">` with `<`, `>` and `&` escaped as `<`, `>`, `&`;
- all text is inserted with `textContent`, never `innerHTML` with data;
- images are relative file paths, never base64 (TAC-003-01);
- browser storage (`localStorage`) is wrapped in `try/catch`; the page works without it.

### D-53 Reference labels through `Evaluator` only

**Decision.** The export gets labels from `Evaluator.label_columns` (TAC-003-03). The labels are shown only after the reveal in blind mode and are named "etykieta referencyjna (AI, niezweryfikowana)".

### D-54 Item selection and order

**Decision.** One item per image–question pair. Priority, highest first:
1. `models_disagree`: tier 1 vs tier 2 answer differ, or the main vs the comparison model differ;
2. `escalated`: tier 2 was asked, or the decision is `abstain`;
3. `label_disagree`: the final answer differs from a `certain` reference label;
4. `near_threshold`: `|max(p) - t1_threshold| <= 0.10`;
5. `control`: the remaining confident answers, in a seeded random order (seed 42).

All items are kept when there are at most `--max-items` (default 100); otherwise the list is cut in this order. Within a group the order follows the sample. Priority reasons are hidden before the reveal, because they would hint at the answer.

### D-55 Feedback file

**Decision.** The page downloads `feedback-<export_id>.json`:

```json
{
  "schema": "map-qa-review-feedback/1",
  "export_id": "…", "exported_at": "…", "downloaded_at": "…",
  "question_set_version": "qs-v1",
  "thresholds": {"t1_threshold": 0.8, "t1_threshold_compare": 0.8, "tier2_accept": "high"},
  "reviewer": "optional name",
  "items": [{
    "item_id": "<photo_id>|<question_id>", "photo_id": "…", "kind": "photo|sign_crop",
    "question_id": "…", "image_sha256": "…",
    "human_answer": "<option>|cannot_decide",
    "image_quality": "sufficient|poor_but_decidable|too_poor_to_decide",
    "flags": ["ambiguous_question", "reference_label_wrong", "other"],
    "comment": "…", "blind": true, "judged_at": "…",
    "verdicts": {"<role>": {"model": "…", "model_answer": "…", "auto": "agree|disagree|null",
                             "override": "agree|disagree|null", "final": "agree|disagree|null", "comment": "…"}}
  }],
  "summary": {"…": "the same agreement table the page shows"}
}
```

Roles: `tier1`, `compare`, `tier2`, `final`, `reference_label`. An item is "judged" when it has a human answer and an image quality rating. The key `image_sha256 + question_id + question_set_version` keeps a judgment valid across reruns from the same cache.

## 3. Consequences

- (+) No new dependencies, works offline, the output is versioned with the other reports.
- (+) The human sees the same image bytes and request text the models saw.
- (-) Browser JavaScript is tested in a real browser (Playwright) rather than by pytest unit tests.
- (-) The feedback is not yet merged into the reports. Next step, if needed: `map-qa review import feedback.json` writing a human-agreement section, and using `too_poor_to_decide` on sign crops to decide whether to re-cut crops from the full photos (ADR-003 amendment).

## 4. Test strategy

| Scenario | Type | Expected result |
|---|---|---|
| Item selection and order | Unit | Priority groups as in D-54, cap at `max_items`, seeded control order |
| Export from cache | Integration (cache built from real captures) / E2E on the real cache | Files written, 0 POST, ledger unchanged, missing cache entry → not reviewable |
| HTML safety | Unit | No base64 longer than 64 characters, `</script>` in data escaped, every `<img>` path exists, no `http` in `src` |
| Page behaviour | Manual QA in Playwright CLI | Blind mode hides answers until answer + quality chosen; reveal; override; reload keeps progress; download produces valid JSON; light and dark screenshots; 0 console errors |
